# Syncing Loci between machines

One operator, several machines, one set of memories. Each machine keeps its own
`memory.db` and works offline; `loci sync <dir>` exchanges *operations* through a
directory that any file-copying tool can carry. Merging is idempotent: running it again
never duplicates memories or resurrects superseded or deleted ones.

## Model

- Memory IDs are UUID v7 and are **preserved** across machines. No ID mapping exists.
- Every database has a stable `machine_id` (UUID v7 generated by the v3 migration, kept
  in `schema_meta`; override with `[sync] machine_id`).
- Every local mutation appends one **op** to `op_log` in the *same transaction* as the
  change. `loci sync` publishes new ops to `<dir>/<machine_id>.jsonl` (one JSON object per
  line, `fsync`'d) and applies the other machines' files.
- A machine only appends to its own file and only reads the others', so there are no write
  conflicts and no merge tool is needed.

```
laptop:  memory.db ──ops──▶ <dir>/<laptop-id>.jsonl ─┐   rsync / unison
devspace:memory.db ──ops──▶ <dir>/<devspace-id>.jsonl ┘◀─ both directions
         ◀────────── apply the other file(s) ──────────
```

## Usage

```
loci sync ~/loci-sync        # or set [sync] dir and run `loci sync`
```

```toml
# ~/.loci/config.toml
[sync]
dir = "~/loci-sync"
machine_id = "laptop"        # optional; letters, digits, '-', '_', '.'
```

`loci sync` applies remote ops first, then rewrites any scrubbed lines in its own file,
then appends its new ops. It prints the ops written, applied, skipped and deferred, new
supersede forks and tombstones. A directory lock (`.loci-sync.lock`) stops two syncs on
one machine from interleaving. The embedding model is loaded only if a remote memory has
to be inserted; both machines must use the same model version.

`memory_stats` (MCP) and `loci stats` report `machine_id`, last sync per remote, pending
local ops, deferred ops and unresolved forks. `sync` itself is deliberately not an MCP
tool; run it from a timer.

## Op format (`v: 1`)

Every line is a JSON object with `v`, `op_id` (UUID v7), `ts` (RFC 3339 UTC), `origin`
(`machine_id`) and an `op`:

```json
{"v":1,"op_id":"…","ts":"…","origin":"…","op":"memory.put","memory":{"id":"…","type":"semantic","content":"…","source_group":"g","scope":"global","confidence":0.9,"created_at":"…","updated_at":"…","metadata":{}}}
{"v":1,…,"op":"memory.supersede","old_id":"…","new_id":"…"}
{"v":1,…,"op":"memory.forget","id":"…","hard":false}
{"v":1,…,"op":"memory.forget","id":"…","hard":true}
{"v":1,…,"op":"relation.put","relation":{"id":"…","subject_id":"…","predicate":"…","object_id":"…","created_at":"…"}}
{"v":1,…,"op":"relation.delete","id":"…"}
{"v":1,…,"op":"noop"}
```

`noop` is what a `memory.put` becomes after its memory is hard-deleted (see below).
`relation.delete` is understood by `sync` but no tool or command emits it yet (relations
only disappear when an endpoint is hard-deleted, which every machine applies itself).

Readers consume only complete (newline-terminated) lines, so a half-written last line is
ignored until it is finished. Unparseable lines and unknown versions are counted and
skipped. Each remote has a byte-offset cursor (`sync_state`); if a remote file shrinks the
cursor resets, which is safe because applying is idempotent.

## Applying ops

Ops from all files (plus previously deferred ones) are applied in `(ts, op_id)` order in
one transaction; the cursors advance only if it commits. Applying never emits ops and
never runs similarity dedup.

| Op | Effect |
|----|--------|
| `memory.put` | Unknown ID: insert under that exact ID, re-embed locally, dedup **off**. Known ID: **no-op** (replicated fields never change after creation, so there is nothing to merge). Hard-tombstoned ID: discarded. Soft-tombstoned ID: inserted as forgotten. |
| `memory.supersede` | Sets `superseded_by` if unset. Old memory missing: deferred. Already forgotten or hard-deleted: ignored. Already superseded by a *different* memory: fork (below). |
| `memory.forget` soft | Tombstone; sets `superseded_by = 'forgotten'` if the memory exists. |
| `memory.forget` hard | Tombstone; removes the memory, its FTS and vector rows and its relations, and scrubs content from the local op log. |
| `relation.put` | Idempotent on the ID and on `(subject, predicate, object)`. Missing endpoint: deferred and retried on later syncs. Endpoint hard-deleted: dropped. |
| `relation.delete` | Removes the relation; a later `relation.put` of the same ID is ignored. |

## Conflicts

- **A delete beats everything for its ID.** Tombstones persist.
- **Forked supersession.** If `A→B` happens on one machine and `A→C` on the other, `B` and
  `C` both stay active, `A.superseded_by` points at the op that is earliest by
  `(ts, op_id)` (the same on every machine), and a `supersede_forks` row is recorded and
  shown in `memory_stats`. Consolidate later (for example supersede one with the other).
  Supersessions made before the first sync are backfilled with the time of that sync.

## What is not replicated

`access_count`, `last_accessed`, confidence decay and `cleanup` are local, use-driven
maintenance; replicating them would make the stores thrash. `confidence` is replicated
only as its value at creation.

- **Compaction** *is* replicated, expressed as the ordinary ops it consists of: a
  `memory.put` for the summary plus one `memory.supersede` per original. If both machines
  compact the same originals, the result is a fork you can consolidate.
- **Promotion** (episodic to semantic) replicates as a normal `memory.put`.
- **Cleanup** (hard-deleting stale, decayed memories) is local: it depends on locally
  decayed confidence and local access times. It records a local tombstone so a replay
  cannot resurrect the memory.
- Soft-delete `reason` text is never put in an op. `loci reset` is local.

## Hard deletes and the containment guarantee

Loci can hold sensitive material that may only be kept as a locator. A hard delete is
therefore designed to remove the content everywhere:

- The `memory.forget` op carries only the ID, never content or a reason.
- On the machine that deletes, and on every machine that applies the op, the memory,
  FTS and vector rows are removed, and `memory_log.details` only ever holds reasons, IDs
  and counts (never memory content). The databases run with `secure_delete = ON`, so freed
  pages are zeroed.
- Not-yet-exported `memory.put` ops for that ID are deleted from `op_log`. Already-exported
  ones become `noop` rows and `loci sync` overwrites the corresponding line in this
  machine's sync file **in place with a same-length `noop`**, so other machines' byte
  cursors stay valid. Deferred remote ops holding the content are dropped.
- Your own `loci reset` scrubs the op log the same way.

Limits: the guarantee covers Loci's databases and the sync files it owns. It cannot
reach copies that your transport, backups or snapshots already made, or `loci export`
files. A local `reason` given to `forget_memory` stays in that machine's own `memory_log`
(as in 0.2.3); don't put sensitive text there.

## Transport (not implemented in Loci)

`<dir>` can be anything that copies files between machines. **Do not use a git
repository:** history keeps content that was later hard-deleted, which breaks the
containment rule. Use `rsync` or `unison` over ssh, run in both directions before and
after `loci sync`:

```
rsync -a  laptop:loci-sync/ ~/loci-sync/        # pull
loci sync ~/loci-sync
rsync -a  ~/loci-sync/ laptop:loci-sync/        # push
```

An in-place scrub keeps the file length but changes its mtime, so rsync and unison pick
it up as an ordinary change. Run the whole sequence from a systemd user timer on Linux or
launchd on macOS.

## Upgrading from 0.2.3

The first run of a new binary migrates an existing database in place (schema v2 to v4).
Memories, supersessions, soft-forgets and relations that already exist have no ops, so the
**first** `loci sync` on a database emits them once (a `sync_backfill` marker in
`schema_meta` prevents repeats) before it applies anything from other machines. Two
machines that each have their own old data therefore just merge.

If a new machine should start as a copy of an old one, `loci export` / `loci import` also
works: import preserves IDs, supersession chains and relation IDs, skips existing IDs
without re-embedding, emits ops for what it inserts, and is a no-op the second time. Note
that an import made with a 0.2.3 binary assigned fresh IDs, so such a copy cannot be
matched to the original and will appear as duplicates after syncing.
